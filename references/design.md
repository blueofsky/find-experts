# find-experts 设计方案

> 目标：在 WorkBuddy 官方专家市场 2.5 万条专家里，按用户的口语化需求定位到合适的专家。
> 状态：已落地（2026-10-23），实际实现与原方案的差异见第七节。
> 日期：2026-10-23

**这是 v1.0 的设计稿，用来说明「当初为什么这么定」，不是现状说明。** 写它时 skill 还叫 `expert-finder`，文中的脚本名和路径都按当时写（`export_wb_token.py` 现在是 `scripts/lib/export-token.py`，凭证从 `~/.workbuddy/` 挪进了 `data/`）。要看现在什么样，以 `SKILL.md` 和 `internals.md` 为准。

---

## 一、问题定义

WorkBuddy 的 skill 有 `find-skills` 这类发现工具，专家侧没有对等物。官方专家中心只能按分类浏览和关键词筛选，而市场实际有 **25391 个条目**（agent 22718 + team 2673），按 100 条/页要翻 254 页。

真实需求的表达方式与专家文本几乎没有字面重合。用户说「我这堆访谈录音想整理成书」，专家写的是「长文档工程」「证据与审校」，关键词搜索直接归零。

---

## 二、边界（先说不做什么）

| 事项 | 结论 | 原因 |
|---|---|---|
| 自动为用户切换/启用专家 | **不做** | 专家是会话级角色，同时只能启用一个，切换会替换当前对话的 agent。skill 无法代劳 |
| 自动调用专家执行任务 | **不做** | 同上。skill 只能产出推荐 + 启用指引 |
| 引入 embedding / 向量库 | **不做** | 实测 BM25 加权已够（见第四节），引入模型依赖收益不明确 |
| 抓取专家详细 prompt（agent md 文件） | **不做** | 只做定位，不做内容分析；且详细 prompt 挂在 COS 上需逐条拉取，成本不成比例 |
| 覆盖账号维度的私有专家 | **不做** | 公开接口只返回 market 清单，私有专家不在其中 |

**这个 skill 的价值就是「精准定位」，不是「自动执行」。** 定位准、理由说得清、告诉用户从哪启用，就够了。按「自动切换」去设计是死路。

## 三、数据层

### 3.1 数据源

```
POST https://www.workbuddy.cn/portal/operation-platform/market/expert/list
Authorization: Bearer <WB_ACCESS_TOKEN>
Body: {"page":N,"page_size":100,"expert_type":"agent|team","sort_by":"reco_rank","sort_order":"desc"}
```

- `page_size` 服务端硬截 100，必须翻页
- 并发 6 抓全量：**25391 条 / 16 秒 / 24.2 MB**，未触发限流
- 实测总数在 20 分钟内从 22690 涨到 22718，是活数据，需要定期刷新

### 3.2 凭证

| 项 | 值 |
|---|---|
| 凭证文件 | `~/.workbuddy/wb-token.env`（`WB_ACCESS_TOKEN`） |
| 生成方式 | `export_wb_token.py` 解密客户端登录态 |
| 解密依赖 | `~/.workbuddy/skills/totorosir-workbuddy-score/scripts/buddy_station.py` |
| 登录态真身 | `%LOCALAPPDATA%\CodeBuddyExtension\Data\Public\auth\workbuddy-desktop.info` |
| 有效期 | 滑动续期，客户端后台自动延展（10-09 到期 11-05，10-23 重跑到期 11-20） |

**这是本方案唯一的脆弱点**：依赖一个第三方 skill 的解密模块。缓解措施见 6.2。

### 3.3 字段取舍

必须保留 `quick_prompts`（3 条「用户会怎么问」示例），它把可检索文本从 `description_zh` 平均 43 字提到 132 字，且句式分布最接近真实 query。**丢掉它召回率会塌**（见第五节对比数据）。

存储字段：

```json
{
  "expert_id": "ex_RW7iokWZpKHT",
  "agent_name": "fbsir-super-partner",
  "type": "agent",
  "name": "知识OPC创业助手",
  "prof": "知识OPC创业助手",
  "cats": ["行业顾问","运营人力","营销增长"],
  "tags": ["机会验证","知识服务","经营复盘"],
  "desc": "帮助知识型创业者将专业方法做成小服务……",
  "qp": ["结合我现有的专业能力和材料……", "……", "……"],
  "uc": 405777,
  "rr": 2661,
  "icon": "https://…png",
  "updated_at": "2026-10-23T07:12:00Z"
}
```

落地为 `data/docs.jsonl`，单行一条，预估 6~7 MB（比原始 24.2 MB 小，因为去掉了 `_en` 字段、`categories` 英文 ID、`homepage` 等检索无关项）。

## 四、检索层

### 4.1 为什么不用 embedding

| 维度 | BM25 加权 | embedding |
|---|---|---|
| 依赖 | 纯 Node 标准库 | 模型 + 向量库（数百 MB） |
| 冷启动 | 加载 7 MB + 建索引，目标 < 2s | 加载模型，秒级到十秒级 |
| 命中可解释 | 能指出哪个词/标签命中 | 只能给相似度分数 |
| 召回效果 | 实测 Recall@10 = 7/7 | 未验证，未见得更好 |

25391 条 × 132 字这个规模，朴素方案反而更可控。

### 4.2 分词

**中文字符 bigram**，不引分词词典。

- 优点：免词典、抗新词、对专有名词（「小红书」「拼豆」）友好
- 缺点：产生少量无意义组合，靠 BM25 的 IDF 自然压掉

### 4.3 字段权重（实测最优）

```
title + profession  ×3.0
tags                ×2.0
description         ×1.0
quick_prompts       ×1.2
```

BM25 参数：`k1 = 1.2`，`b = 0.75`（长度归一到语料均值）。

### 4.4 排序公式

```
final = bm25_score × (1 + 0.12 × log10(1 + use_count) / 7)
```

- `use_count` 中位 53、最高 11114261，用 log 压缩后最高加成约 12%，作用是温和惩罚长尾噪声条目，不主导语义排序
- `use_count` 缺失（25391 条里约 14% 无此字段）时按 0 处理，不额外惩罚
- `reco_rank` 只做最终 tie-break（数字小的优先），不参与主分——它是运营权重，与需求无关
- `display_position`（运营置顶）**完全不参与排序**，那是市场页的运营位

### 4.5 召回与精排

```
用户需求 → BM25 召回 top 20 → agent 精排 → 输出 top 3
```

为什么需要 agent 精排：字面相似 ≠ 需求匹配。实测「小红书写了半年没起色怎么涨粉」，加权后 top1 是 `深度思考小组`、top2 是 `里程碑教练`，真正的 `小红书爆款文案手` 只排第 3——因为 quick_prompts 里「内容」「策略」这类泛词把不相关条目顶上来了。

agent 层不做任何外部调用，就是读这 20 条然后判断。

## 五、可行性验证（已跑完，数据真实）

语料：25391 条全量。测试集：7 个口语化需求，人工标注正确答案。

| 配置 | 结果 |
|---|---|
| 只用 name/profession/desc/tags/cats | top1 大面积出错 |
| 加 quick_prompts，无字段权重 | 5 个需求里 4 个 top1 正确，小红书那条仍错 |
| 加 quick_prompts + 字段加权 | **Recall@10 = 7/7**，6 个 top1 正确 |

失败样本（只用基础字段时）：

| 需求 | 被错误排到第一的专家 | 原因 |
|---|---|---|
| 公司想卖老股套现，报价怎么判断 | 潮玩手办与收藏品选购顾问 | 「判断」二字字面命中 |
| 帮我审代码有没有安全漏洞 | 造价工程专家 | 「审」字命中 |
| 孩子高考 600 分能上什么学校 | 高考作文阅卷专家 | 没有「志愿填报」的字面重合 |

加权后全部纠正。完整用例与每轮参数记录在 `references/tuning.md`。

**这个测试集的局限必须写进方案**：仅 7 条，且由我按数据覆盖面构造，存在选择偏差。真实需求跑起来大概率没这么漂亮，权重需要拿实际问题再调。

## 六、更新与维护

### 6.1 刷新流程

```
node scripts/update.mjs
```

三步：① 调 `export_wb_token.py` 刷新 token → ② 翻页拉全量 → ③ 重新生成 `docs.jsonl` + `meta.json`。全程约 25 秒。

建议频率：**每周一次**，或 skill 首次使用前若 `meta.json` 里的生成时间超过 7 天则自动提示。

### 6.2 凭证失效的降级路径

`buddy_station.py` 属于第三方 skill，有再次下架的可能。三级降级：

1. **首选**：当前链路（`totorosir-workbuddy-score` → `buddy_station.py`）
2. **替代**：SkillHub 上还有走 WBIPC 通道、完全不碰 token 的同类 skill（`workbuddy-checkin-daemon`、`workbuddy-reward-wbipc`），可借用其 IPC 代发能力
3. **兜底**：skill 内置明确的失败提示，让用户手工粘贴一页 JSON 或从浏览器导出，`update.mjs` 支持 `--from-file <path>` 导入

如果三条都断，skill 仍可用旧索引提供服务，只是数据变旧——`meta.json` 会显示数据日期，skill 输出时一并告知。

## 七、目录结构（落地版）

```
~/.workbuddy/skills/expert-finder/
├── SKILL.md                  # 触发词 + 三步流程 + 输出模板 + 退出码对照
├── scripts/
│   ├── find.mjs              # 检索入口（--json / --top / --cat / --type / --refresh）
│   ├── update.mjs            # 刷新（token 预检 → 抓取 → 护栏 → 原子替换）
│   ├── selftest.mjs          # 7 个回归用例，改权重后必跑
│   └── lib/
│       ├── text.mjs          # bigram 分词 + 字段权重 + BM25 参数
│       ├── index.mjs         # 二进制索引 build/read
│       ├── fetch.mjs         # 接口分页抓取（并发 6，重试 3 次）
│       ├── token.mjs         # 凭证读取、JWT 过期判断、自动刷新
│       └── export-token.py   # 从客户端登录态解 token（复用 buddy_station）
├── data/
│   ├── index.bin             # 46 MB：文档正文 + 倒排表，单文件
│   ├── meta.json             # 状态、条数、分类分布、token 到期、失败原因
│   └── history.json          # id → [first_seen, last_seen]，1.2 MB
└── references/
    └── tuning.md             # 权重演进、失败样本、规模变化
```

**相对原方案的两处改动**

1. **合并 `docs.jsonl` 与索引为单个 `index.bin`**。原方案两个文件分开写，会出现"新正文 + 旧倒排"的中间态。改成一个文件后，一次 `rename` 就是完整快照，读方（含并发读）永远看到一致数据，也让"检索时惰性更新"变得安全。
2. **索引改为 update 时预构建的二进制倒排表**，不再每次查询重建 tf 表。实测单次查询 0.5 秒（含读 46 MB 文件），其中检索本身 5~13 ms。

## 八、接口设计

### 8.1 检索命令

```bash
node scripts/find.mjs "我这堆访谈录音想整理成书" --top 20 --json
```

可选参数：

| 参数 | 说明 |
|---|---|
| `--top N` | 返回条数，默认 20 |
| `--cat <名称>` | 限定分类，如 `技术工程` |
| `--type agent\|team` | 限定单专家或团队 |
| `--json` | 输出机器可读 JSON（agent 用这个） |

### 8.2 输出结构

```json
{
  "query": "我这堆访谈录音想整理成书",
  "total": 25391,
  "data_updated": "2026-10-23",
  "hits": [
    {
      "rank": 1, "score": 51.5, "id": "ex_9WJTqJnv6NTd",
      "name": "福帮手", "prof": "长文档写作与改稿专家",
      "type": "agent", "cats": ["内容创作","运营人力"],
      "tags": ["长文档工程","多场景创作","证据与审校"],
      "desc": "轻松几十万字，不跑题，没有AI味……",
      "qp": ["这堆访谈笔记、扫描件和表格，我要写成几十万字的正式稿……"],
      "uc": 592178, "icon": "https://…"
    }
  ]
}
```

### 8.3 SKILL.md 输出模板（给用户看的）

```markdown
按「<用户需求>」在 25391 个专家里筛出 3 个：

1. **福帮手** · 长文档写作与改稿专家
   命中理由：quick_prompts 里就是「这堆访谈笔记、扫描件和表格，我要写成几十万字的正式稿」
   使用量 59.2 万 | 分类：内容创作

2. …

怎么启用：左侧边栏「专家」→ 搜索名字 → 启用（注意同一时间只能启用一个专家）
不想切专家的话，当前会话我也能直接干这件事。
```

最后那句兜底必须有——大多数需求不需要真的切专家。

## 九、验收标准

| 项 | 标准 | 验证方式 |
|---|---|---|
| 召回质量 | 7 个回归用例 Recall@10 ≥ 6/7 | `references/tuning.md` 的用例集 |
| 精排质量 | top3 里至少 1 个被人工判定为「合适」≥ 5/7 | 人工过一遍 |
| 检索延迟 | 单次查询 < 3 秒（含冷启动加载） | 计时 |
| 数据新鲜度 | `meta.json` 显示日期在 7 天内 | 查看 meta |
| 降级可用 | 断网时能基于本地索引返回结果并标注数据日期 | 断网测试 |
| 可解释性 | 每条推荐能说出命中的字段与原文片段 | 看输出 |

## 十、落地步骤

| 阶段 | 内容 | 产出 |
|---|---|---|
| 1 | `lib/bm25.mjs` + `lib/fetch.mjs` | 检索与抓取内核 |
| 2 | `update.mjs` 生成 `docs.jsonl` | 7 MB 索引 |

| 4 | 跑 7 个回归用例，调权重 | `tuning.md` 记录 |
| 5 | `SKILL.md` + 输出模板 | skill 可被触发 |
| 6 | 你用真实需求试 3~5 个，按结果再调 | 反馈 |

预计阶段 1~5 一次做完，阶段 6 需要你的实际问题。

## 十一、已定的四件事

1. **存储**：本地 `~/.workbuddy/skills/expert-finder/data/`，不放资料库。46 MB，本地读一次 0.5 秒。
2. **更新频率**：TTL 7 天 + 每天 04:30 定时刷新（定时任务 id `772c9f1a`）。定时任务成功时 TTL 永不触发；失败时惰性机制兜住，只在输出末尾提示一句。
3. **team 保留**：团队 2677 条与 agent 混排，用 `type` 字段区分，`--type` 可过滤。理由是有些需求确实团队更合适（如「做一份行业研究报告」召回的 top1 就是券商产业研究团）。
4. **输出语言**：推荐文案中文，字段名英文。
